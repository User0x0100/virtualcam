## 测量方法

机器为 AMD Ryzen 9 4900HS，8 核 / 16 逻辑处理器，Windows 11 Pro build 26300。所有正式样本为 release 构建，1080×1920、30 FPS；每个版本/负载预热 3 秒、测量 15 秒，重复两次，顺序为事件第一轮、轮询第一轮、轮询第二轮、事件第二轮。两边使用相同测量源码，轮询版使用归档的旧源码及其匹配的 producer，避免 wire v1/v2 混用。

本次测量客户端整体以管理员身份运行，方便直接读取 Local Service 进程 CPU；这扩大了权限使用范围。后续测量应让生产端/客户端以普通权限运行，仅通过管理员采样器读取确实受限的服务信息。本记录不冒充普通权限应用的完整性能验证。

CPU 来自进程 GetProcessTimes 的 kernel + user 时间差。FrameServer 的 100% 单核百分比表示占满一个逻辑核；合计整机容量百分比为 FrameServer 加 benchmark 进程（生产线程和 MF 客户端）的单核百分比之和除以 16，**不是额外采集的系统总 CPU 计数器**。CPU/FPS 按采样时长合并。

生产线程在每帧写入前，把单调时钟微秒数编码进亮度块，客户端在 ReadSample 返回且缓冲可读后解码。延迟包括 host 写入、跨 Session Frame Server 和 Source Reader 路径，不是 source 内部单次 copy 或纯事件唤醒延迟。帧内时间戳通过 NV12 → YUY2 转换保真测试。表中 p50/p99 是两次运行各自分位数的均值，**不是合并全部原始样本后的分位数**；空闲黑帧没有生产者时间戳，因此不计算延迟。

## 正式对照

每格顺序均为 **轮询版 → 事件版**。

| 负载 | FrameServer CPU，单核 % | 两进程合计，整机容量 % | p50 延迟 ms | p99 延迟 ms | 实际 FPS |
| --- | ---: | ---: | ---: | ---: | ---: |
| NV12 原生直通 | 5.41 → 4.53 | 0.624 → 0.806 | 3.58 → 3.65 | 5.12 → 6.02 | 30.00 → 30.00 |
| NV12 → source 转 YUY2 | 11.24 → 9.62 | 1.086 → 1.031 | 5.60 → 4.93 | 7.39 → 6.58 | 30.00 → 30.00 |
| 生产端直接写 YUY2 | 6.34 → 4.64 | 0.828 → 0.771 | 4.24 → 3.54 | 5.87 → 5.32 | 30.00 → 30.00 |
| 无生产者黑帧 | 4.58 → 3.75 | 0.582 → 0.517 | — → — | — → — | 29.05 → 29.05 |

所有带生产者的正式运行均约 30 FPS，时间戳重复数为 0。空闲黑帧两版均约 29.05 FPS，未把少交帧造成的 CPU 下降当作收益。

**不能得出“所有路径 CPU 和延迟都改善”的结论。** 原生 NV12 的宿主 CPU 从 5.41% 降到 4.53% 单核，但 benchmark 客户端/生产端从 4.58% 升到 8.38% 单核，合计整机容量从 0.624% 升到 0.806%（相对增加约 29.2%）；延迟中位数没有稳定改善。转换 YUY2 和生产端直接写 YUY2 的合计 CPU 分别相对下降约 5.1% 和 6.9%，p50 分别降低约 0.67 ms 和 0.70 ms。

尾部也不是全面改善：事件版原生 NV12 的平均 p99 更高；事件版直写 YUY2 出现单次最大 22.46 ms，而轮询版该负载最大 7.50 ms。两次短窗测量不足以证明稳定的全场景性能收益；没有固定核心亲和或 CPU 频率，客户端 CPU 上涨的具体原因尚未定位。

## 测试中发现并修复的帧率回退

最初事件版 `c90a898` 使用 WaitForMultipleObjects 的毫秒超时作为空闲期限，真实 Session 0 的无生产者黑帧约为 21.1 FPS。新增 `frame_server_idle_delivery_follows_native_rate` 在旧 DLL 上测到 21.56 FPS、按预期失败；改为高精度 waitable timer 后通过，正式大尺寸测量约 29.05 FPS。此修复为 `a5bbbc0`。

前面的短窗口冒烟数据，以及被执行工具超时中断的批次均排除在正式对照之外。测试产生的中途残留摄像头已清理。

## 复现

先以版本化路径安装当前 release MF source（管理员权限），然后运行：

```powershell
cargo build --release -p virtualcam-mf
cargo run --release --example managed_camera -- install-mf 'C:\Program Files\VirtualCamRs\mf-14e409ef1990\virtualcam_mf.dll'
cargo test --test windows_mf -- --ignored --test-threads=1 --nocapture
cargo run --release --example mf_delivery_bench -- nv12 15 1080 1920 30
# 其余负载：convert、yuy2、idle
cargo test --example mf_delivery_bench
```

需要管理员权限读取 Local Service 进程 CPU。切换基线时必须同时切换匹配的 producer，并在无客户端时重启 FrameServer 以确认加载对应 DLL；结束后恢复事件版。不得覆盖进程仍加载的 DLL。
